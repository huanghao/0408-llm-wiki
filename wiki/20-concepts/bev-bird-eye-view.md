# BEV：Bird's Eye View（鸟瞰图表示）

BEV 是自动驾驶感知和规划的核心坐标表示——把三维世界投影到地面平面的俯视图。这个词本身几十年前就有，但"从摄像头学习生成 BEV 特征"是 2020 年后深度学习领域的核心议题。

---

## 什么是 BEV

把传感器采集的三维世界"压扁"到地面平面，从正上方俯视观察：

```
         摄像头/LiDAR 视角（3D）      →    BEV（2D 俯视）
         ──────────────────                ──────────────
         有透视变形、遮挡、深度模糊          位置/尺寸/方向直观
         近大远小，距离难判断               和地图对齐，多传感器统一坐标
```

**坐标系（自车中心）**：

```
         x ↑（车头方向，前方）
         y ←（向左，侧方）
         z  （高度，BEV 里通常忽略或单独处理）
```

每辆车在 BEV 里是一个有朝向的矩形框，位置 = (x, y)，朝向 = yaw 角，和地图直接叠加。

**和地图叠加的好处**：高精地图（车道线、停止线、路口形状）本身就是 BEV 坐标格式。把感知结果和地图对齐，意味着可以直接回答"这辆车在哪条车道上""距离停止线还有多远"——不需要任何坐标转换，直接相减就行。

---

## 为什么不直接用 3D？

这是个好问题。3D 信息更丰富，为什么不直接用 3D 来做规划和预测？

**原因 1：大多数驾驶决策只发生在地面平面。** 车不会飞，行人也基本在地面行走。规划路径、判断碰撞、跟随车道，全部发生在 z≈0 的地面上。保留完整 3D 不但没有用，还大幅增加计算量。

**原因 2：3D 处理的代价非常高。** 完整 3D 场景需要 voxel（体素）表示，一个 100m×100m×10m 的空间在 0.5m 分辨率下有 200×200×20 = 800,000 个格子，而 BEV 只需要 200×200 = 40,000 个。计算量差了 20 倍。这就是为什么 3D occupancy（OCC）方法到 2022-2023 年才起步，而 BEV 2020 年就成熟了。

**原因 3：真正需要高度信息的场景，再补充就好。** 路牌、立交桥、行道树的高度对规划有影响，这时候用 TPV（三视图）或 OCC（体素）来补充高度维度，而不是一开始就全用 3D。

## 为什么自动驾驶喜欢 BEV

| 需求 | BEV 的优势 |
|------|-----------|
| 规划路径 | 路径在地面平面，BEV 直接对应 |
| 预测他车轨迹 | 轨迹在 BEV 里，位置/速度/朝向都是绝对距离（米），可以直接计算碰撞时间 |
| 多传感器融合 | 摄像头、LiDAR、雷达在同一 BEV 坐标系下自然对齐 |
| 多帧时序拼接 | 自车 ego-motion 补偿后，不同时刻的 BEV 可以直接叠加 |
| 下游任务 | 碰撞检测、可行驶区域、车道保持都在地面平面 |

**"BEV 之前轨迹不也一目了然吗？"** —— 不然。在摄像头图像里，同一帧看到两辆车，你无法从像素坐标直接知道它们各自距离你多远。一辆车占图像 100 像素可能在 10m 处，另一辆占 50 像素可能在 5m 处——近大远小，距离和像素大小没有线性关系。基于 LiDAR 的系统从来就能直接给 3D 坐标，BEV 的意义是让**摄像头**也能输出和 LiDAR 同格式的结果，而不用 LiDAR。

**具体例子**：前方有两辆车。
- 图像空间：左车占 80×40 像素，在图像中间偏左；右车占 60×30 像素，在中间偏右。无法直接计算距离、车速、碰撞时间。
- BEV 空间：左车中心在 (15m, -2m)，朝向 5°，速度 (10m/s, 0)；右车中心在 (25m, 1.5m)，朝向 0°，速度 (8m/s, 0)。两行数字，规划器直接拿去算。

## 两个时代：经典 BEV vs 学习 BEV

### 经典 BEV：IPM（Inverse Perspective Mapping）

**核心思路**：如果地面是平的，那么摄像头图像里每个在地面上的像素点，都对应地面上唯一一个真实坐标。知道相机的安装高度和俯仰角，就能算出来。

**图示：IPM 正常工作时**（侧视图，x = 前方，z = 高度）

```
               摄像头
                 ○  (安装高度 h = 1.5m)
                /|
               / |
  φ=10° 的射线/  | h = 1.5m
             /   |
            /    |
──────────●──────●────────────────── z = 0 (地面)
          ^      ^
          地面标记  摄像头在地面的投影
          x = h/tan(φ) = 1.5/tan(10°) ≈ 8.5m 前方
```

**具体计算**：像素在图像中位置决定了射线方向角 φ（相对水平面向下的角度）：

```
φ = 10°  →  地面距离 x = 1.5/tan(10°) ≈  8.5m
φ =  5°  →  地面距离 x = 1.5/tan(5°)  ≈ 17.1m
φ =  2°  →  地面距离 x = 1.5/tan(2°)  ≈ 43.0m
```

越接近图像中心（φ 越小），对应越远的地面位置——这就是"近大远小"的本质，IPM 把它反算回来。

**图示：IPM 失效时**（以行人为例）

```
正确理解（行人在 15m 处，高 1.7m）：

               摄像头 ○
                      \  φ ≈ 3.1° 的射线
                       \
                        ● ← 射线打到行人头部 (x=15m, z=1.7m)
                        |  行人身高 1.7m
──────────────────────● ──── z = 0
                       ^
                    行人真实位置 15m

IPM 的错误计算（强行假设 z=0）：

               摄像头 ○
                      \  同一条射线 φ ≈ 3.1°
                       \
                        \
                         \
──────────────────────────●── z = 0
                           ^
                   IPM"计算"出的位置 ≈ 28m  ← 错了 13m！
```

**为什么偏差这么大**：行人头部在 1.7m 高处，而 IPM 认为"射线打到地面"，所以把射线延伸到更远处才交到 z=0。高度越高（如路牌 3m）、偏差越大；在平地上的白色标线（z=0）则没有任何偏差。

所以 IPM 只能用于平整路面上的二维标线（车道线），不能用于有高度的目标。

### 学习 BEV：2020 年后的主流

**思路**：让神经网络**学习**如何把图像特征映射到 BEV 空间，不依赖平地假设。

关键演进（都在 wiki 里有文档）：

| 时间 | 论文 | 核心机制 |
|------|------|---------|
| 2020 | **Lift-Splat-Shoot**（Philion & Fidler, ECCV 2020）| 预测深度分布，把图像特征"抬升"到 3D 点云，再沿高度轴压缩到 BEV |
| 2021 | **BEVDet**（Huang et al.）| 把 LSS 接入检测头 |
| 2022 | **[BEVFormer](../30-papers/bevformer-2203.17270.md)**（Li et al., ECCV 2022）| 预定义 BEV 查询 + 空间交叉注意力（从图像采样）+ 时序自注意力 |
| 2022 | **[BEV-LaneDet](../30-papers/bev-lanedet-2210.06006.md)**（Wang et al.）| MLP 线性映射 + Virtual Camera 统一相机参数 |
| 2023 | **[TPVFormer](../30-papers/tpvformer-2302.07817.md)**（Huang et al., CVPR 2023）| 三个互相垂直平面替代单一 BEV，处理任意高度物体 |

## BEV 的具体形式

### 栅格 BEV（Rasterized BEV）

把 BEV 平面划分为等间距网格，每个格子存储特征向量：

```
BEV 特征图：[H, W, C]
H = 前后方向格数（如 200，对应 100m，0.5m/格）
W = 左右方向格数（如 200，对应 ±51.2m）
C = 每格的特征维度（如 256）
```

**具体例子**：BEVFormer 的 200×200 BEV 覆盖自车周围 [-51.2m, 51.2m] 的正方形区域。如果前方 20m 有一辆车，它的中心落在大约第 140 行（从后往前数）第 100 列（正中间）的格子附近，该格子的 256 维特征编码了这里"有车"的信息。

**计算量分析**（以 BEVFormer 为例）：

```
BEV 格子数：200 × 200 = 40,000 个
每个格子的空间交叉注意力：6 相机 × 4 参考点 × 4 采样点 = 96 次特征采样
每层 BEV 编码器：40,000 × 96 = 约 400 万次操作
6 层编码器：约 2,400 万次操作

对比 Backbone（R101，6 路 900×1600 图像）：
  6 × 900 × 1600 = 约 860 万像素，经过多层卷积
  实测：BEVFormer 推理总耗时约 540ms，其中 Backbone 占 391ms（72%）
```

**结论**：BEV 编码器本身不是瓶颈，**Backbone 才是**。这是为什么更换更轻的 Backbone（R18→BEV-LaneDet 272 FPS）或减少图像输入分辨率能大幅提速，而减少 BEV 格子数（200→100）只节省一小部分时间。

400K 格子的密集 BEV（稀疏 BEV 的动机）才是真正需要优化的方向——见上方"稀疏 BEV"一节。

### 向量化 BEV（Vectorized BEV）

不用栅格，而是直接预测场景中语义元素（车道线、停止线、人行横道）的几何点集。

**具体例子**：MapTR 的输出里有一条左侧白色虚线：

```
元素类型：Lane Divider（单白虚线）
点序列：(5m, -1.5m) → (10m, -1.6m) → (20m, -1.8m) → (40m, -2.1m)
# 以上坐标都在 BEV 平面的 (x=前方距离, y=横向位移)
```

规划器看到这个，直接知道"左侧 1.5m 处有一条向左弯的车道线"，不用再解析栅格特征图。

更紧凑（只存在的元素才占空间），适合下游规划直接使用。

### 稀疏 BEV

只对有目标的区域生成特征，不维护全局密集网格。

**具体例子**：假设摄像头检测到 3 辆车和 2 个行人，稀疏方法只为这 5 个目标生成查询特征，而不是计算 40,000 个格子。Sparse4D、SparseDrive 等 2023 年后的方法走这条路，速度提升 5–10×。

代价是如果有遗漏目标（没被初始检测到），就永远拿不到它的特征——稀疏方法对"找到所有目标"的召回率要求更高。

## 关键区别：BEV 表示 vs BEV 生成方法

这两个概念容易混淆：

| | 说明 | 举例 |
|---|---|---|
| **BEV 表示** | 用 BEV 坐标系描述输出（车道线、检测框在 BEV 里）| 所有 BEV 论文都有 |
| **BEV 生成方法** | 从摄像头图像生成 BEV 特征图的技术（IPM / Lift-Splat / Transformer）| 不同论文用不同方法 |

**具体例子**：同一个任务"检测前方行人在 BEV 里的位置"：

- **BEVFormer** 的做法：6 路摄像头图像 → Transformer 空间交叉注意力（从图像采样特征）→ 生成 200×200 栅格 BEV 特征图 → 检测头输出 `(12m, 0.5m)` 处有行人。
- **BEV-LaneDet** 的做法：前视摄像头图像 → Virtual Camera 归一化 → MLP 线性映射 → 生成 200×40 栅格 BEV 特征图 → 检测头输出车道线坐标。

两者的**输出**（BEV 坐标）格式相同，但**生成 BEV 特征的过程**完全不同。这就像同样说"给我一张北京地图"，可以从卫星拍，可以从街景拼，可以从激光雷达扫——最终都是地图，但生成方式各异。

## BEV vs OCC（3D Occupancy）

这是另一个常见混淆点（comment #5 的直接回答）：

| | BEV | OCC（3D Occupancy）|
|---|---|---|
| **维度** | 2D 地面平面 | 3D 体素空间（含高度）|
| **表示** | 每个格子 = 地面上一块区域 | 每个格子 = 空间中一个立方体 |
| **能表示什么** | 地面上的目标：车道线、车辆、行人（投影到地面）| 任意高度的目标：路牌、树木、建筑物、桥梁 |
| **计算量** | 200×200 = 40K 格子 | 200×200×20 = 800K 体素（20× 更多）|
| **典型用途** | 目标检测、车道线、规划 | 可通行空间建模、3D 场景理解 |
| **wiki 代表** | BEVFormer、BEV-LaneDet、MapTR | TPVFormer、VoxFormer、Occ3D |

**形象例子**：

- **BEV** 看到的场景：地图上有一辆车在 (10m, 2m)，有一条车道线，有可行驶区域。**看不到**：桥下面有行人、路牌在 3m 高空、桥墩占了某个空间。
- **OCC** 看到的场景：每个 0.5m×0.5m×0.5m 的立方体都标注了"空"或"被什么占据"。桥墩的每一层体素都是"建筑物"，3m 高的路牌体素是"路牌"，桥下行人的体素是"行人"。

**为什么不都用 OCC？** 计算量。OCC 的格子数是 BEV 的 20 倍，且要额外解决高度方向的特征获取问题（摄像头看不到遮挡后面的体素）。OCC 是 BEV 发展成熟后，2022-2023 年才大规模出现的任务。

**2023 年以后 OCC 的发展**：

| 时间 | 方向 | 代表工作 |
|------|------|---------|
| 2022 | 工业界先行 | Tesla AI Day 2022：Occupancy Networks，第一次在量产车上用体素表示 3D 空间，实时推理 |
| 2022–2023 | 学术建立 benchmark | Occ3D（wiki 已有）、SurroundOcc、OpenOccupancy；Waymo/nuScenes 数据集上的评测标准逐步统一 |
| 2023 | 时序 OCC | OCC + 多帧融合，利用历史帧提升遮挡区域的预测质量 |
| 2024 | 4D OCC / FlowOcc | 不只预测"这个体素是什么"，还预测"它在下一帧会移动到哪"，把 OCC 和**感知层的运动表示**合并（见注）|
| 2024 | OCC → 规划 | OCC 作为规划的输入，直接回答"这个体素能不能走"，跳过显式目标检测 |
| 2025+ | 生成式 OCC | 用扩散模型/NeRF 生成完整 3D 场景（包括遮挡区域），做数据增强和仿真 |

**注：运动预测在 AD 栈里的位置**

自动驾驶的处理流程是：感知 → 预测 → 规划 → 控制。运动预测夹在感知和规划之间，但它更偏向感知：

```
感知（Perception）：  世界现在是什么样的？（检测/跟踪目标）
        ↓
预测（Prediction）：  世界接下来会是什么样的？（预测他车轨迹）
        ↓
规划（Planning）：    自车应该怎么走？（决策+路径规划）
        ↓
控制（Control）：     执行指令
```

- **传统做法**：三层分离——感知输出当前目标位置，预测模块（MTR/TNT/Wayformer）接收后输出他车未来轨迹，规划模块再基于轨迹做决策。
- **4D OCC / FlowOcc** 的定位：属于**感知层的扩展**——它把"这个体素当前是什么"和"这个体素将要往哪移动"合并成一个统一的场景表示，输出的是丰富化的空间表示，不是高层决策。可以理解为：把原来感知→预测之间的信息压缩到一张"带方向箭头的地图"里。
- **端到端系统（UniAD/DriveVLM）**：感知、预测、规划三层共享同一个 BEV 特征图，边界模糊——这类系统里运动预测是中间的隐式表示，既不单独"归感知"也不"归规划"。

**一句话**：运动预测传统上比感知更靠近规划侧，但比规划更偏向"理解世界"；4D OCC 把运动信息下沉到感知表示层，跟规划的距离反而更远了。

**当前状态（2026）**：OCC 已是自动驾驶感知的标配任务，和目标检测、车道线检测并列。主流量产方案（Tesla、华为 ADS、理想、小鹏）都在用某种形式的 OCC。OCC 正从"独立感知任务"演变为"场景表达中间层"，下游直接对接规划和 World Model。

## 三视图（TPV）：BEV 的扩展

BEV 只有地面平面（忽略高度），对于 3D occupancy 预测不够用。TPVFormer 把 BEV 扩展为三个互相垂直的视图：

```
BEV（俯视，H×W）  +  Front（前视，H×D）  +  Side（侧视，W×D）
```

三视图合并可以表示 3D 空间中任意位置的语义。详见 [TPVFormer 文档](../30-papers/tpvformer-2302.07817.md)。
