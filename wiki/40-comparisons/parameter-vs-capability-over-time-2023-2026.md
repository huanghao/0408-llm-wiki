# 参数量 vs 能力：2023–2026 的时间压缩

一句话总结：过去三年的主线不是“参数越来越大”，而是“达到相近能力所需参数量越来越小”；但到 2025 以后，这条曲线已经明显分裂成通用聊天、推理、代码三种不同轨道。

## 先说限制

这页比较的是：

- **公开参数量**的模型
- 加上**公开 benchmark、官方博客、公开评测口径**里的能力信号

它不是全行业完整曲线，因为很多最强闭源模型并不公开参数量，例如：

- GPT-4 / GPT-4o
- Claude 3 / 3.5 / 3.7
- 大部分 Gemini 商用版本

所以这页回答的是：

- **按时间维度看，已公开参数量模型里，达到某类能力大概要多大参数量，这个门槛怎么变了？**

而不是：

- “所有模型的真实参数-能力函数是什么”

## 总结先给

如果只看公开参数量模型，最稳的粗估是：

| 时间对比 | 大致结论 |
|---------|---------|
| 2023 → 2024 | 7B–13B 从“入门/实验”变成“真能用” |
| 2024 → 2025 | 4B–8B 开始覆盖不少 2024 年 13B–32B 的使用区间 |
| 2024 → 2026-05 | 达到相近可用能力所需参数量，大致压缩了 **2x–5x** |
| 激进口径 | 某些家族和官方对比口径下，可见 **10x+** 的压缩 |

但这只是总览。真正看细了之后，至少要拆成三个章节：

1. 通用聊天
2. 推理
3. 代码

## 为什么不能只盯参数量

参数量今天仍重要，但已经不再是最主导变量。过去三年真正改变曲线斜率的是：

1. **数据质量**
2. **后训练质量**
3. **专项化分层**
4. **MoE**

所以这页所有“等效参数量”都只能理解成：

- 大致使用区间接近
- 不是逐 benchmark 严格一一等价

## 2023–2024 的总转折

2023 年的默认直觉仍是：

- `7B`：可研究、可微调，但很多真实任务还只是“能跑”
- `13B`：开始像样
- `70B`：明显更稳得多

这时参数量仍然很像能力主旋钮。

到了 2024，`phi-3-mini 3.8B` 这类模型开始给出强信号：

- 整体平均分接近 `GPT-3.5`
- 在不少公开 benchmark 上超过更大的 7B 模型

这意味着：

- 小模型不再只是轻量替代品
- 参数曲线开始被数据质量和后训练明显撬开

但 2024 还只是转折点，不是完全改写点。

## 一、通用聊天：参数门槛在稳步下移

### 2023

通用聊天直觉大致是：

| 参数量 | 大致体验 |
|---:|---|
| `7B` | 能聊，但很容易露出“模型味” |
| `13B` | 开始像样 |
| `70B` | 明显更稳、更全面 |

### 2024

`phi-3-mini 3.8B` 说明：

- 3.8B 已经开始进入“可以认真拿来当通用助手”的讨论区间

但更稳妥的 2024 区间还是：

| 2024 参数量 | 通用聊天定位 |
|---:|---|
| `3B–4B` | 轻量可用，适合简单助手 |
| `7B–8B` | 真正形成日常可用门槛 |
| `13B–14B` | 本地助手里更稳的主力层 |
| `32B` | 高质量单机通用助手开始成立 |
| `70B` | 仍然是显著更稳的高端层 |

### 2025

这年最强的压缩信号来自：

- `Qwen3-4B` 可与 `Qwen2.5-72B-Instruct` rival
- `OLMo 2 32B` 接近 `Qwen 2.5 72B` 和 `Llama 3.1 / 3.3 70B`
- `Gemma 3 27B` 进入高端通用体验比较

最稳的经验改写是：

- `14B–32B` 已成为“高质量通用助手”的主战场

### 2026-05 粗估

| 2024 需要的大致参数量 | 2026-05 大致能压到 |
|---:|---:|
| `70B` | `14B–32B` |
| `32B` | `8B–14B` |
| `13B–14B` | `4B–8B` |

如果只记一句：

- **通用聊天这条线的稳结论是 2x–5x 参数压缩。**

### 通用聊天最容易误读的点

- `4B` 开始进入一些旧 `70B` 模型的竞争区间，不等于全面替代旧 `70B`
- 通用聊天比代码、数学更依赖主观偏好、多轮交互和风格稳定性

## 二、推理：压缩更激进，但更依赖 test-time compute

### 2023

公开参数量模型里的直觉仍是：

- 更强推理通常要更大模型
- 小模型的 reasoning ceiling 还比较低

### 2024

`phi-3-mini 3.8B` 和 `phi-4 14B` 的信号说明：

- 推理不再完全由参数量主导
- 高质量数据和后训练可以显著压缩所需参数

### 2025

这是推理曲线真正断裂的一年：

- `DeepSeek-R1` 把 reasoning 做成单独后训练层，并蒸馏到 `1.5B / 7B / 8B / 14B / 32B / 70B`
- `QwQ-32B` 说明 `32B` 推理专模本身已可成类
- `Qwen3` 把 thinking / non-thinking 合进统一使用方式

所以 2025 以后谈推理能力，至少有三个轴：

1. 参数量
2. 后训练路线
3. 推理时 token 预算

### 2026-05 粗估

| 2024 普通模型的大致推理能力层 | 2026-05 reasoning model 可能压到 |
|---:|---:|
| `70B` | `14B–32B` |
| `32B` | `7B–14B` |
| `13B–14B` | `3B–8B` |

但一定要配一句警告：

- **这些“压缩”通常伴随更长思考链和更高推理时开销，不是白拿的。**

### 推理最容易误读的点

- `14B` 推理模型打赢 `70B` 通用模型，不代表参数已经不重要
- 2025 以后推理能力的一大来源是**推理时多生成 token**

## 三、代码：变化最大，范式也变了

代码这条线要单独强调，因为它不是简单的“能力更强了”，而是：

- **评估对象变了**
- **系统边界变了**

### 2023：代码能力主要看补全和单题 benchmark

当时的核心问题通常是：

- HumanEval 多高？
- 多大参数量能写出正确函数？

代表性模型和范式：

- Code Llama
- StarCoder
- 各类 7B / 13B / 34B code-specialized models

这一代的基本直觉是：

- 更大模型通常更稳
- `34B+` 明显强于 `7B`
- code benchmark 还是以 function-level completion 为主

### 2024：小中模型开始接管大量实际编码场景

有两层变化。

#### 1. 通用小模型已经开始会写代码

`phi-3-mini 3.8B` 这类模型已经在 HumanEval 上给出不错结果。  
这说明：

- `3B–8B` 这档开始能覆盖很多日常 coding assistance

#### 2. Qwen2.5-Coder 把“本地代码助手”做成完整尺寸带

根据现有 wiki 和官方博客：

- `Qwen2.5-Coder` 首发 `1.5B / 7B / 32B`
- 后续扩成 `0.5B / 1.5B / 3B / 7B / 14B / 32B`
- 代码预训练规模 `5.5T tokens`
- `128K context`

它的意义不是“出一个强代码模型”，而是：

- 第一次把本地代码助手按硬件层级完整铺开

### 2025：代码模型从“写代码”升级到“做软件工程”

这是代码曲线真正断代的一年。

#### 1. 评测对象变了

真正重要的已经不只是：

- HumanEval
- MBPP
- pass@1

而是：

- RepoQA
- SWE-Bench
- Browser-Use / Tool-Use
- agentic coding task completion

也就是说，代码模型开始被要求：

1. 读懂整个代码库
2. 规划修改步骤
3. 调用工具
4. 执行、测试、修复

#### 2. Qwen3-Coder 直接把 agentic coding 当主战场

根据官方口径：

- `Qwen3-Coder-480B-A35B-Instruct`
- `35B active`
- `256K` 原生上下文，可外推到 `1M`
- 直接对标：
  - SWE-Bench Verified
  - Agentic Tool-Use
  - Browser-Use

这代表代码模型竞争的范式已经变了：

- 不再只是“谁写函数更像答案”
- 而是“谁更像一个能在真实工程环境里干活的 agent”

#### 3. 执行反馈和工具环境成为第一等公民

代码这条线进步快的根本原因是：

- 代码是可验证的

模型可以接到很强的客观信号：

- 单元测试通过没通过
- 程序能不能运行
- patch 会不会破已有行为

这让代码模型很适合：

- execution-based filtering
- verifier
- tool-augmented RL

### 2026-05：代码能力最好按三层理解

#### 第一层：轻量代码补全 / IDE 辅助

典型参数：

- `1B–4B`

足够做：

- 补全
- 改写小函数
- 解释局部代码
- 简单单文件修复

#### 第二层：个人主力代码助手

典型参数：

- `7B–14B`

大致接管了以前很多更大模型的日常编码场景：

- 多文件修改
- repo 内导航
- 单元测试驱动修复
- 中等复杂度重构建议

如果只记一个最稳的代码参数压缩结论，就是：

- **很多原来得 `34B–70B` 才比较稳的代码工作流，今天 `7B–14B` 已经能做。**

#### 第三层：高端 repo-level / agentic coding

典型参数：

- `32B+`
- 或者 `MoE + 长上下文 + 工具环境`

这层更像：

- 软件工程代理底座

真正决定体验的，常常不是总参数量，而是：

1. active 参数量
2. 上下文长度
3. 工具调用策略
4. 执行反馈

### 代码最稳的时间压缩结论

| 2023–2024 旧代码能力层 | 2026-05 大致能压到 |
|---:|---:|
| `34B–70B` 的稳代码工作流 | `7B–14B` |
| `13B–34B` 的日常代码助手 | `3B–8B` |
| `7B–13B` 的轻量补全助手 | `1B–4B` |

但要补一句：

- 对 repo-level / agentic coding，不存在那么简单的单参数映射

### 代码最容易误读的点

- 代码模型进步不再等于 HumanEval 进步
- 强代码模型通常不只是“通用模型加一点代码数据”
- 高端代码能力已经从“参数量问题”变成“系统设计问题”

## 现状与影响

- 一句话定性：2023–2026 的主线不是“参数越来越大”，而是“参数效率越来越高”；其中代码这条线变化最大。
- 最稳结论：
  - 通用聊天：`70B -> 14B–32B`
  - 推理：压缩更激进，但要连同 test-time compute 看
  - 代码：`34B–70B -> 7B–14B` 是最值得记的一档
- 最重要的范式变化：
  - 通用聊天：更稳的小中模型接手旧大模型区间
  - 推理：reasoning model 独立成层
  - 代码：从 `pass@1` 到 `repo understanding` 再到 `agentic coding`
