# 自动驾驶数据工程

自动驾驶的数据挑战和 LLM 有一个根本性的相似——**数据飞轮**：更好的模型发现更多 corner case → 标注 → 训练更好的模型。但具体挑战不同：标注成本高 3 个数量级、长尾场景稀缺、多模态时间戳对齐。

## 必看：理解数据引擎（Data Engine）范式

1. **Tesla AI Day 2021 / Karpathy CVPR 2021**（演讲，非论文）  
   搜索："Andrej Karpathy CVPR 2021 Tesla FSD"  
   看点：业界最成熟的数据引擎描述——从部署车队自动挖掘 hard case，到人工标注，到模型改进的完整飞轮。这个范式和 Llama 3 用小模型实验预测大模型效果的逻辑是同构的。

## 两个领域的核心共同点

| | LLM | 自动驾驶 |
|--|-----|---------|
| 质量过滤 | 困惑度 + fastText | 模型不确定性 + 人工复核 |
| 数据飞轮 | 更好模型 → 更好过滤 | 部署 → 发现 corner case → 标注 |
| 合成数据 | LLM 生成文本（Phi） | 生成模型合成场景（DriveDreamer） |
| 少量高质量 | LIMO/LIMA | Tesla 数据引擎精选 hard case |

先把 LLM 这条线（[DoReMi](../30-papers/doremi-2305.10429.md) + [Phi-1](../30-papers/phi-1-2306.11644.md)/[Phi-3](../30-papers/phi-2-phi-3.md) + [LIMO](../30-papers/limo-2502.03387.md)）读完，再看自动驾驶，会发现是同一套思维的不同模态应用。

### 展开：自动驾驶的质量过滤——模型不确定性 + 人工复核

LLM 用困惑度（KenLM 打分）过滤低质量文本；自动驾驶没有"困惑度"这样的通用信号，但有一个等价物：**模型自己不确定的地方，就是需要人工关注的地方**。

具体做法：
- **感知不确定性**：目标检测模型对某帧的预测置信度低于阈值（比如 3D box 置信度 < 0.5），或者多个模型版本对同一帧的预测不一致——这帧被标记为"模型不确定"。
- **预测偏差**：车辆行驶后，可以把预测模型当时的输出和日志里记录的真实轨迹做事后对比——如果预测的 minFDE（最近条终点误差）超过阈值，说明这个场景是预测模型的弱点，应该被回收用于训练。这是模块化系统的优势：每个模块都有可测量的输出，可以事后量化误差并精准定位训练弱点。一段式 E2E 里，如果网络只有最终规划轨迹输出（纯黑盒），确实无法区分是"预测错了"还是"规划错了"；但 UniAD 这类有显式中间表示（跟踪 query、预测轨迹、占据图）的一段式模型，也可以事后查看中间输出做溯源——这正是 UniAD 在工程上保留显式中间任务的原因之一，不只是为了训练信号。
- **规划异常**：规划模块触发了 fallback（降速、急刹），或者人类接管了车辆控制——这是最强的"模型失败"信号。

这些信号自动触发人工复核队列：标注员只看被标记的帧，不需要审查所有数据。**效率比例大约是 1:100**——1 个标注员处理的有效数据量，相当于随机抽查时的 100 倍。

这就是"模型不确定性 + 人工复核"的完整含义：模型作为过滤器，人工作为质量保证的最后一关。

### 展开：自动驾驶数据飞轮——部署 → 发现 corner case → 标注

这是自动驾驶数据工程最核心的机制，Tesla 在 AI Day 2021 上描述得最清楚。

飞轮的每一圈：

1. **部署**：把当前模型推送到路上的车队（Tesla 有百万量级车辆，国内头部公司也有数千到数万辆测试车）。
2. **自动挖掘**：车辆在行驶中持续上传传感器数据，后台系统自动检测"触发器"——模型不确定的帧、人类接管事件、规划异常、特定场景标签（如"夜间雨天左转"）。这一步完全自动化，每天可以从数百万公里行驶数据中筛出数千个高价值 clip。
3. **标注**：被挖掘出的 clip 进入标注队列，人工精标（3D box、轨迹、语义分割）。标注的是模型最弱的那些场景，而不是随机样本。
4. **训练**：用新标注数据 fine-tune 或重训模型，模型在这些 corner case 上变强。
5. **回到第 1 步**：更强的模型上车，能发现更细微的异常，触发下一轮更高质量的数据挖掘。

**和 LLM 数据飞轮的对比**：LLM 的飞轮是"更好的模型过滤出更好的训练数据"（DCLM 的核心逻辑），自动驾驶的飞轮是"部署到真实世界才能发现真实的失败模式"。前者是闭环的，后者必须有真实部署才能转动——这是自动驾驶数据工程比 LLM 更依赖硬件规模的根本原因。

### 展开：Tesla 数据引擎精选 hard case

[Tesla 数据引擎（Data Engine）](../00-overview/tesla-data-engine.md)是上述飞轮的工程实现，Karpathy 在 CVPR 2021 和 Tesla AI Day 2021 中描述了核心机制：

**触发器系统（Trigger System）**：工程师定义"我想找什么场景"，系统在全车队数据里自动搜索。比如：
- "找所有在有遮挡情况下切入本车道的车辆"
- "找所有 FSD 预测和人类实际操作不一致的路口场景"
- "找所有夜间降雨中的行人横穿"

触发器可以基于感知输出、规划输出、人类接管信号，也可以基于地图信息（特定路口类型）。每个触发器定义一类 hard case。

**精选逻辑**：同一类触发器可能匹配几十万条 clip，但标注资源有限。系统会进一步按"多样性"和"难度"排序——优先标注模型最不确定、且和已有标注数据最不相似的 clip。这和 LIMA 的逻辑完全一致：**不是随机采样，而是主动找模型最弱的地方**。

**规模**：Tesla 公开过的数字是每天处理约 160 万个视频 clip，其中经过触发器筛选后进入精标的约 1 万条（筛选比例约 0.6%）。这 1 万条的标注价值，远高于随机抽取的 100 万条。

这就是"少量高质量"在自动驾驶侧的具体含义——不是数据少，而是**标注资源集中在模型最需要的地方**。

## 系统架构演变对数据工程的影响

在看完 Wayformer/MTR/UniAD 之后，一个自然的问题是：**这些模型在工业界处于哪个位置，还在被使用吗？**

### 三种主要架构路线

**模块化（Modular）**：感知 → 预测 → 规划 → 控制，各模块独立训练、独立验证，通过结构化数据接口交互。Waymo 是代表，内部预测模块就是 MTR++ 风格，每个模块有独立的评测标准（WOMD leaderboard 就是预测模块的标尺）。

**端到端一段式（E2E）**：摄像头图像直接输出规划轨迹或控制信号，中间表示是 latent feature 而非可读的结构化数据。Tesla FSD v12+ 是代表，完全去掉了 C++ 规划模块，由神经网络一步到位。

**两段式（Two-stage E2E）**：折中方案——感知模块独立（输出结构化 3D box/地图），PnC 部分（预测+规划）端到端联合训练。华为 ADS 3.0（GOD 网络 + PDP 规划网络）、小鹏 XNGP 新版本采用类似路线。

| 路线 | 代表 | 输入 | 优点 | 缺点 |
|------|------|------|------|------|
| 模块化 | Waymo | 传感器原始数据 | 可验证、可 debug、安全论证清晰 | 工程成本高，误差累积 |
| 一段式 E2E | Tesla FSD v12+ | 摄像头图像 | 训练数据规模驱动、端到端优化 | 可解释性弱，安全认证难 |
| 两段式 E2E | 华为 ADS 3.0 | 感知结构化输出 | 感知可独立升级，PnC 联合优化 | 接口设计复杂 |

### 预测+规划联合模型（不带感知）

两段式里有一个值得单独关注的子类：**接收感知给出的结构化场景描述（agent 状态 + 地图），直接输出自车规划轨迹，中间不拆分"预测"和"规划"两个独立步骤**。这类模型不带感知模块，输入已经是向量化的场景表示（和 Wayformer/MTR 一样），但输出除了他车预测轨迹，还包含自车的规划轨迹。

这是比"只做预测"更进一步、比"端到端感知+规划"更聚焦的方向，适合在有成熟感知模块的两段式系统里替换 PnC 部分，也适合在 nuPlan 这类用结构化数据的 benchmark 上研究。

代表性工作：

- **GameFormer**（ICLR 2024，清华）：把预测和规划统一成博弈框架——自车和他车的未来轨迹联合建模，用 level-k 博弈迭代精化（每一轮都考虑"对方会怎么反应"）。输入和 Wayformer/MTR 格式相同（polyline 向量化场景），输出自车规划 + 他车预测联合结果。是理解"预测和规划如何互相影响"的最清晰案例。
- **PLUTO**（2024）：Prediction + PLanning Using Transformers，在 nuPlan benchmark 上性能很强，同类思路。
- **PDM 系列**（nuPlan 基线）：nuPlan 上大量基线就是"结构化输入 → 直接规划"，不带感知。
- **MTR-e2e**（MTR++ 变体）：把 MTR 的 K=64 压缩到 K=6，联合预测自车+他车，是 MTR 向预测+规划一体化的初步尝试。

**数据工程角度**：这类模型的训练数据需求和纯预测模型类似——GT 是日志里记录的真实轨迹（他车轨迹做预测 GT，自车轨迹做规划 GT），不需要额外的人工标注。区别在于需要 nuPlan 或类似包含自车决策的数据集，而不只是 WOMD 这类只标注他车的预测数据集。

### Wayformer/MTR 风格的预测模块还在用吗

**在模块化和两段式架构里：仍然是核心组件。** Waymo 的 WOMD leaderboard 持续更新，MTR++ 系列到 2025 年还在前列。只要系统里有独立的预测模块，就需要这类方法。

两段式里预测模块的必要性不只是"展示给人看"。规划模块需要知道"周围车辆未来 8 秒可能去哪"才能做出安全决策——比如要不要变道、要不要减速让行。预测输出的轨迹分布直接输入规划的 cost function。没有预测，规划只能基于当前帧做反应式决策，无法提前规避冲突。预测精度低会导致规划做出错误的让行或加速决策，是安全风险的直接来源。

从标注角度看，预测模块的 GT 是他车的真实未来轨迹（从日志里直接读取，不需要人工标注），训练成本低；但在评测时，预测误差会被一路传递到规划决策，所以预测质量直接影响整体系统的安全性，不是"辅助任务"。

**在一段式 E2E 里：显式预测模块消失了**，"预测"功能被隐式融入 latent 表示——预测不再有独立输出，但仍然在网络内部发生。

**UniAD 是什么**：严格来说是一段式 E2E——图像进、规划轨迹出，但内部有显式的预测中间表示（agent trajectory queries）。它是学术界的标杆，不是工业界直接部署的方案（计算代价太高，五个模块串联在车端难以实时运行）。

**推理时不使用未来信息**：预测模块只使用过去 1-2 秒的历史观测，输出对未来 8 秒的预测。推理时没有任何"未来信息"输入——这是必要约束，否则无法在真实驾驶中部署。训练时 GT 轨迹来自日志回放（事后已知），不是"偷看未来"，而是用历史数据学习"给定过去，预测未来"的映射。

**PnC 预测和自回归的关键区别**：PnC 在每一帧都用真实传感器观测重新预测未来，看起来像是"用当前真实信息+上一帧预测的未来"在循环，但这和 GPT 的自回归有本质不同：

| | GPT 自回归 | PnC 每帧预测 |
|--|-----------|------------|
| 下一步输入 | 模型自己上一步的**输出** | 传感器的**真实观测** |
| 误差传播 | 累积——第 t 步的错误会影响第 t+1 步 | 不累积——每帧独立从真实观测出发 |
| 已生成输出的命运 | 持续被引用，驱动后续生成 | 被下一帧的真实观测**替换**，不再使用 |

PnC 里上一帧预测的"未来 8 秒他车轨迹"，不会被下一帧的预测模型作为输入——下一帧预测直接从传感器观测到的真实他车位置重新出发。预测输出只给当前帧的规划模块用（决定"我现在该怎么开"），然后就被丢弃了。这也是为什么预测错误不会像 LLM 幻觉那样"越来越离谱"——每 100ms 真实世界就把误差清零一次。

### 对数据工程的影响

架构路线的选择直接影响数据标注需求：

- **模块化**：每个模块需要独立标注数据（感知需要 3D box，预测需要轨迹 GT，规划需要专家轨迹），数据标注成本高但质量可验证
- **一段式 E2E**：只需要专家驾驶轨迹作为 GT（不需要 3D box 标注），大幅降低标注成本，但需要极大规模的行驶数据（Tesla 靠百万量级车队）
- **两段式**：取决于感知模块的输出格式。若感知输出 3D box，则需要 box 标注；若感知输出 occupancy（occ，体素级占据预测），则不需要 box 标注，只需要 occ GT（可从 LiDAR 点云自动生成，标注成本低得多）。华为 ADS 3.0 的 GOD 网络就是输出 occ，PnC 部分以 occ 为输入，整条链路不需要手工 box 标注。

**感知输出格式的选择**直接影响标注成本：

| 感知输出 | GT 来源 | 标注成本 | PnC 输入信息量 |
|---------|---------|---------|--------------|
| 3D bounding box | 人工精标 | 高（逐帧逐目标）| 类别、位置、速度（结构化）|
| Occupancy（occ） | LiDAR 点云自动生成 | 低 | 空间占据（稠密但无语义）|
| 两者结合 | 混合 | 中 | 最完整 |

这解释了为什么 Tesla 可以用更少的标注预算但更大的数据量——它的 GT 主要是专家驾驶轨迹，标注颗粒度粗，靠数据规模补偿精度。而 occ-based 两段式（如华为路线）通过降低感知标注成本，在数据规模和标注质量之间找到另一种平衡。
